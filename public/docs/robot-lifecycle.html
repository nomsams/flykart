From a racer to a room companion

Rewards tell a trainer which offspring did well. Sensors tell a deployed controller what is happening. A robot should not need an invisible simulator reward field, exact checkpoint direction, or object coordinates to act.

1. Preserve the racer and add eyes

Export the racer from FlyKart. The original racer uses exact simulator measurements; those are observations, distinct from its fitness rewards and penalties. The vision lab replaces those measurements with camera estimates. Select eyes and “seeing only”; pose-indexed lap memory and any feeling-only comparison are not deployment evidence.

For actual controller evolution exclusively through the camera, use the new script. It uses pixel-derived estimates, optional sonar, and body feedback; exact progress, contact and lap completion only rank candidates externally. It excludes exact scene cues, coordinate mission values and pose-indexed lap memory. Eyes stay fixed; retrain eyes in the existing vision training pipeline when the renderer or sensor changes.

npx vite-node scripts/visual-racer.ts --from=my-racer.json --eyes=public/vision/robot/vision-net.json --out=training/my-visual-racer.json --gens=10 --pop=6 --workers=1
# Optional later stage: add --sonar=true
# Quick wiring smoke test, not meaningful training: --gens=1 --pop=2 --episodes=2 --ticks=30

The script refuses an existing output or anything under public/. It preserves the source, writes a combined fly + eyes offspring and a report, and validates on different tracks, seeds, styles and chassis variation. It never regenerates Claude's trained assets.

2. Transfer input meanings, then learn visual room skills

A track brain and a room brain both have 17 base inputs, but these inputs mean different things. “Adapt racer to room + sonar” preserves recurrent weights, motor output weights and biases, remaps body speed / previous steering / previous drive plus the comparable static-obstacle input, and zeroes incompatible road and new goal inputs. New sonar weights start at zero for a 17-input racer. The parent checkpoint is retained inside the journey manifest. This is a transfer hypothesis, not a guarantee of successful navigation.

Choose a room and the approach or follow skill. Set the real ball's diameter and sample its colour from the raw real-camera preview. The task network reads 35 named channels: eight RGB patch means, valid sonar, previous issued motor commands, visible colour centroid and area, optional contact switch, camera-derived light and validity flags. It never reads position, reward, pain, score, task success or target coordinates.

“Collect 3 camera-only coach episodes & train” uses an explicitly labelled visual teacher, then trains a 35 → 16 → 2 tanh network. Two whole episodes train it; the third checks action imitation. Demonstrations are downloadable. The coach sees the same visual observations; its colour-following rule is hand written. Imitation error is not task success. The camera CNN is still the bundled fixed eye network; the new trainable task network learns visual actions from patch pixels and visible target cues.

Use the learned network, then “Evolve fly in this room.” Each candidate receives a cloned fly and task network; offspring mutate both, while the elite stays intact. Candidates share start pose, room, task and noise seeds. Visual and reward memories reset between trials; online sugar association weights are frozen for fair comparisons. “Inherited fly action mix” determines how much of the spiking fly's action survives in the final action. At zero, this task network alone controls the robot; this is not a claim of a biological fly connectome.

3. Sugar, simulated pain and fading help

Approach pays sugar once when the axle centre reaches a clearance band beside the visible target. Following requires a continuous interval at a comfortable distance; losing the band resets that interval. The solid blue sphere remains in the camera. It is not physically carried or pushed by the chassis. Scripted motion illustrates following and does not simulate a rolling ball.

Optional approach shaping rewards the difference in distance between consecutive steps; stationary proximity cannot repeatedly pay. Its strength decreases between generations, so every candidate in a generation sees the same schedule. Keep the terminal success reward rather than simply withdrawing all sugar. Contact “pain” is a configurable simulated negative teaching signal, independent of whether a contact switch is installed. Episode scoring also retains the baseline contact/time costs shown in the training bench.

Held-out neural tests freeze weights, disable the coach, disable approach shaping and record success/contact/time/score on three unseen target seeds with mild sensor noise. They restore the original lab afterwards. Three trials are a smoke test, not statistical proof; repeat in different rooms, with different target colours/sizes, lighting, occlusion and distractors.

The distance-difference term is a practical evolutionary training aid. We do not claim policy invariance for this evolutionary objective or its fading schedule. Ng, Harada & Russell (1999) prove invariance under specific potential-based shaping conditions; those conditions should not be casually extended here. Research on Drosophila memory updating describes how omitting an expected reward can extinguish approach. Felsenberg et al. (2018) describe opposing reward and punishment memories. The software uses engineered learning rules and does not reproduce those biological circuits.

4. Modular sensors and virtual swarms

ModuleSimulation / hardware contract
CameraActual delivered RGB pixels and validity. Disable to test a visual ablation.
HC-SR042–400 cm return or unknown. Disable both close and validity channels to train camera only.
Collision switchOff by default. Installed virtual switch reads contact; disabled gives zero and “not installed.” Physical USB arming refuses this module until a real channel and wiring adapter exist.

The named observation schema and validity channels make missing sensors explicit; exports reject incompatible task-network schemas. A future hardware sensor needs a firmware reading, GPIO/wiring validation, unit/noise model and matching observation adapter. Merely turning on a simulated checkbox does not add real hardware.

Virtual swarm members share one camera and inspect separate gaze or zoom patches. Configure member decision weights and confidence, mean or median voting in the vision panel. The task network receives the centre camera; the inherited fly action can include swarm voting. More Kenyon cells are available through the existing memory controls. Larger memory and more looks add compute; neither is claimed to improve recognition until measured. These are virtual processing members, not a fleet of independent physical robots.

5. Rehearse deployment and prepare future fetching

Export the full fly + eyes or the complete lab to keep the task network, sensor settings, colour calibration, parent lineage and held-out evidence. A plain FlyKart brain export contains only the inherited spiking circuit; use the combined export for the task skill. The journey manifest alone does not contain the complete room or camera CNN.

Use floor-mark calibration for forward/backward motion, left/right turns, squares, command offset, measured tracker correction, heading PID and uncertainty filtering. USB-host inference uses the same task-network weights and raw-pixel feature adapter as simulation, with frozen learning. It receives no simulated reward evaluator. The existing pin-map attestation, independent firmware watchdog, sensor timeout, explicit ARM and PWM cap apply. The demonstration coach cannot arm physical motors. Hardware performance is unmeasured until tested on the actual car.

For onboard operation, the compact student must be distilled from demonstrations/replays of the intended task and evaluated again after quantization. It is a separate compressed controller with a fixed 30-channel feature schema, not the full task network/fly/swarm. Existing firmware flashing requires compiled binaries and explicit device selection; no physical robot is flashed automatically.

Fetching is a future skill. It needs an actual gripper or scoop, a possession sensor or validated visual estimate, release control, a visible home/person cue and a staged approach → acquire → return → release evaluator. This chassis has none of those actuators. Rewarding proximity to a ball is not evidence that it picked up or delivered the ball.
